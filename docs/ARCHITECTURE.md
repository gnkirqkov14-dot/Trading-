# Архитектура

Демо приложение за автономен AI трейдър (крипто + ETF), работещ изцяло с
виртуален капитал (paper trading). Този документ описва компонентите, как
комуникират, и къде вече е предвидено бъдещото разширение до "approval mode".

## 1. Компоненти и комуникация

```
┌─────────────────────────────────────────────────────────────────────┐
│                         Scheduler (APScheduler)                      │
│         тик на всеки ANALYSIS_INTERVAL_MINUTES (по подразбиране 4ч)  │
└───────────────────────────────┬───────────────────────────────────────┘
                                 │ извиква
                                 ▼
┌─────────────────────────────────────────────────────────────────────┐
│                    Pipeline (app/pipeline.py)                        │
│  за всеки актив от watchlist-а: risk-exit проверка → нова обосновка  │
└──────┬───────────────┬───────────────┬───────────────┬───────────────┘
       │                │               │               │
       ▼                ▼               ▼               ▼
┌────────────┐  ┌───────────────┐ ┌───────────────┐ ┌──────────────────┐
│ news.py    │  │ statements.py │ │ technical.py  │ │ risk.py          │
│ новини +   │  │ изказвания +  │ │ CoinGecko /   │ │ лимити на позиция│
│ сентимент  │  │ тон/важност   │ │ Stooq + RSI/  │ │ SL/TP по подразб.│
│            │  │               │ │ MACD/SMA/S-R  │ │ autonomous_mode  │
└─────┬──────┘  └───────┬───────┘ └───────┬───────┘ └────────┬──────────┘

                        ▼                                     │
              ┌────────────────────────┐                      │
              │  decision_engine.py    │◄─────────────────────┘
              │  претегля сигналите,   │
              │  извиква Claude API за │
              │  reasoning (или fallback)│
              └───────────┬─────────────┘
                           ▼
              ┌────────────────────────┐
              │      portfolio.py      │
              │  paper trading engine: │
              │  Position / Trade /    │
              │  PortfolioSnapshot     │
              └───────────┬─────────────┘
                           ▼
              ┌────────────────────────┐
              │   PostgreSQL / SQLite   │  (SQLAlchemy ORM, app/models.py)
              └───────────┬─────────────┘
                           ▼
              ┌────────────────────────┐
              │   FastAPI REST API      │  (app/routers/*)
              │  /portfolio /decisions  │

                           ▼
```

Всеки от четирите входни модула (новини, изказвания, технически анализ,
риск настройки) е независим и комуникира с `decision_engine.py` само през
обикновени Python структури (dict/TypedDict) — няма скрито споделено
състояние. Това прави лесно заместването на всеки модул с реален доставчик
на данни, без да се пипа останалата верига.

## 2. Защо тези технологии

| Слой | Избор по подразбиране | Причина |
|---|---|---|
| Backend | Python + FastAPI | Асинхронен, добра поддръжка на Pydantic схеми (= директно съвпада с JSON формàта на решенията), лесна интеграция с APScheduler и Anthropic SDK |
| База данни | SQLite (demo) / PostgreSQL (prod) | SQLAlchemy ORM работи с двете без промяна на кода — само `DATABASE_URL` в `.env` |
| Frontend | React + Vite + Tailwind + Recharts | Бърз dev цикъл, компонентен UI за таблото/дневника, leightweight графики без нужда от TradingView лиценз в демо фаза |
| LLM | Claude API (Anthropic) | `decision_engine.py` подава суровите сигнали и иска претеглена, естествено-езикова обосновка — точно ролята "reasoning", а не просто класификация |
| Пазарни данни (крипто) | CoinGecko `market_chart` (free/demo tier) | Без нужда от ключ за демо честотата на заявки, достатъчно за 90-дневна дневна серия |
| Пазарни данни (ETF) | Stooq CSV endpoint | Безплатен, без ключ, дневни свещи за SPY/QQQ и др. |
| Новини / изказвания | Mock генератори с adapter seam | Реалните доставчици (GNews, NewsAPI.ai, TwitterAPI.io/Sorsa — виж таблицата в промпта) изискват платени ключове; демото работи "from day one" без бюджет, а превключването към реален доставчик е локална промяна в `_fetch_real_news` / `_fetch_real_statements` |

## 3. Поток на едно решение

1. Scheduler-ът (или ръчен `POST /analyze/run`) стартира `run_pipeline()`.
2. За всеки актив от watchlist-а: ако има отворена позиция, първо се
   проверява дали текущата цена е пробила stop-loss/take-profit нивото
   (`portfolio.check_risk_exit`) — това затваряне е винаги автоматично,
   независимо от режима на автономност (вижте т. 4).
3. Ако позицията не е затворена принудително, `decision_engine.synthesize_decision`
   тегли новини + изказвания + технически индикатори, изчислява претеглен
   резултат (`_combine_signals`) и решава `buy` / `sell` / `hold`.
4. Обосновката (`reasoning`) идва от Claude API, ако е зададен
   `ANTHROPIC_API_KEY` — Claude вижда суровите, понякога противоречиви
   сигнали и трябва изрично да ги претегли в 3-5 изречения. Без ключ се
   ползва `_rule_based_reasoning` — детерминиран шаблон върху същите числа,
   така че демото работи и без платен LLM достъп.
5. Решението се записва в `decisions` таблицата (винаги — включително
   `hold`, за да остане пълен дневник), после `portfolio.execute_decision`
   го изпълнява срещу виртуалния портфейл (ако не чака одобрение).
6. След обхождане на целия watchlist се записва `PortfolioSnapshot` — това
   захранва графиката на таблото.

## 4. Approval mode (предвидено, но неактивно в демото)

Изискването е ясно: **в демо версията агентът е напълно автономен**, но
архитектурата вече носи всичко нужно за бъдещ режим с ръчно одобрение:

- `RiskSettings.autonomous_mode` (bool) и `RiskSettings.approval_threshold_pct`
  (float) — вече персистирани, редактируеми през `PUT /settings/risk` и
  видими в UI-то (Настройки → "Режим на автономност").
- `decision_engine.synthesize_decision` вече изчислява
  `requires_approval = (not autonomous_mode) and (size_pct >= approval_threshold_pct)`
  за всяко решение.
- `portfolio.execute_decision` проверява точно това поле: ако е `True`,
  сделката **не** се изпълнява — решението се записва със статус "чака
  одобрение" вместо да бъде изпълнено автоматично.
- Стоп-лос/тейк-профит изходите (`check_risk_exit`) съзнателно заобикалят
  тази проверка — те винаги се изпълняват веднага, защото затварят
  съществуваща позиция за управление на риска, а не отварят нова
  дискреционна експозиция.

С други думи: превключването на `autonomous_mode` на `False` в demo базата
данни (или през UI-то) веднага активира одобрителния режим — не е нужна
промяна в кода. Остава само да се добави механизъм за самото одобрение
(напр. endpoint `POST /decisions/{id}/approve` + push/имейл известие) —
следваща стъпка извън обхвата на демото.

## 5. Разширяемост

- **Нови активи**: добавяне на ред в `WATCHLIST` (`app/config.py`).
- **Нов доставчик на новини/изказвания**: имплементиране на
  `_fetch_real_news` / `_fetch_real_statements` в съответните модули.
- **Реални пари**: вижте `docs/REGULATORY_NOTES.md` — изисква лицензиране
  и сериозни compliance стъпки, извън обхвата на демото.
